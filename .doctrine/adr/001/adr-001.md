# ADR-001: Queue state lives on the entry

## Context

org-iw queues point at existing Org documents and headings that the user
edits in place (PRD-001). The queue state (membership and order) has to
live somewhere. Prior art keeps it apart from the content: mir.el uses a
managed import/archive, org-roam-review keeps its own metadata, and
bjsi/incremental-writing uses a separate queue. A separate store can
drift from the notes, needs the package to be readable, and breaks when
notes are refiled or edited outside Emacs.

## Decision

We will store all queue state as Org properties on the entries
themselves: `IW_<QUEUE-ID>: <signed integer rank>`, one property per
membership, read locally (never inherited). Queue views and orderings are
always derived from source entries. No queue file, database, persistent
index, review log or recovery journal is authoritative or required. An
in-memory index is permitted only as a disposable copy that the source
buffers invalidate. Queue *definitions* (display names, vocabulary) live
in Elisp configuration, not in entries.

## Consequences

### Positive

- The metadata can be read and edited by hand without the package, and it
  diffs and merges in Git like the rest of the notes.
- Refile, copy and ordinary editing carry membership with the entry.
- Nothing needs syncing, migrating or repairing.

### Negative

- Every ordering has to be found by scanning sources, so performance
  depends on corpus size (PRD-001 OQ-1).
- Global operations such as redistribution touch many files.
- Hand edits can introduce invalid ranks or duplicate IDs, which have to
  be diagnosed.

### Neutral

- Renaming a queue ID means rewriting properties; display names can
  change freely.
- `IW_AFTER_<Q>` is reserved for future snoozing under the same model.

## Verification

- Tests assert that every read comes from source buffers or files, and
  that no auxiliary file is created (REQ-025).
- Design review: any proposed persistent store must supersede this ADR.
