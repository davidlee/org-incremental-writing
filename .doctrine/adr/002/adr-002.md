# ADR-002: Writes go through visiting buffers; single writer

## Context

Queue operations modify the user's writing files. Those files are often
open with unsaved drafts. Writing to disk behind a live buffer loses work
or triggers "file changed on disk" conflicts. Saving a buffer to persist a
queue change can silently save half-finished writing. The corpus is
almost entirely under Git.

## Decision

We will make every change through a buffer visiting the file (opening it
if needed) and treat live buffer contents, including unsaved changes, as
authoritative over disk.

- Save policy: a buffer that was unmodified before the operation is saved
  after it. A buffer that was already modified is left unsaved, and the
  user is told the queue change is unsaved. Nothing is ever written to
  disk behind a live buffer.
- Single-entry operations rely on normal buffer undo. There is no
  cross-file undo log.
- org-iw assumes one active Emacs writer. It claims no transactional,
  atomic or multi-instance guarantees. Multi-file work (batch add,
  redistribution) reports partial completion, and recovery is by Git and
  normal buffer tools.

## Consequences

### Positive

- Unsaved writing is never lost or silently saved.
- Undo works as the user expects.
- Behaviour is ordinary Emacs, with nothing hidden.

### Negative

- A queue change in a dirty buffer isn't on disk until the user saves.
- Multi-file operations can partially fail and need manual recovery.
- Visiting many files (batch add, redistribution) has a buffer cost
  (PRD-001 OQ-2).

### Neutral

- Git is the recovery mechanism by convention; org-iw does not automate
  Git.

## Verification

- Tests with initially clean and initially dirty buffers assert the save
  policy (REQ-021).
- Tests assert that disk contents never override live-buffer state
  (REQ-006).
- Multi-file tests simulate a write failure and check the partial-completion
  report (REQ-020).
