# ADR-003: Four layers with a fixed dependency direction

## Context

The riskiest logic in org-iw is ordering: placement, rank allocation,
detecting exhausted gaps, and redistribution plans. The riskiest side
effects are Org mutations and saves. Tangling the two makes ordering hard
to test and invites parallel implementations of "the current queue". The
brief asks for a small separation, not a framework.

## Decision

We will structure the code in four layers. Each layer may depend only on
the layers beneath it:

1. **Ordering core (pure).** Queue-ID rules, property-name
   classification, placement, rank allocation, tie order and
   redistribution plans, all over plain data. No buffers, no Org, no I/O.
2. **Discovery and resolution.** Finds source files and live buffers,
   reads memberships, resolves entries by ID, produces diagnostics.
   Returns plain data to the core.
3. **Org mutation.** Sets or removes one property and ensures an ID, all
   through visiting buffers and under the save policy (ADR-002).
4. **Commands and view.** Interactive commands, session context, queue
   view and configuration UI. Composes the layers below; holds no
   ordering logic.

Each layer has one owner per concept (POL-002). Layers map to files. No
public data API is promised until the interactions stabilise.

**Ownership at the boundaries** (amended 2026-10-01, REV-002):

- Every guard on a write, including file, buffer, stale-value and
  drawer-shape checks, lives in the mutation layer's preflight, so every
  caller gets it.
- Every reader of Org structure and every scan query lives in discovery,
  behind public (non-`--`) functions. Mutation and commands read the
  entry only through them; the mutation layer may depend on discovery.
- Commands compose the layers and let their refusals surface. They own
  only their own preconditions (session, point, typed input).

## Consequences

### Positive

- The ordering core is exhaustively unit-testable without Org fixtures.
- There is one place to change each concern, and duplication is easy to
  spot.

### Negative

- Plain data has to be passed across boundaries (entry records, not
  markers everywhere). This is a small translation cost.

### Neutral

- The layers structure the code, not the delivery order. Slices cut
  through them vertically (RFC-001).

## Verification

- Byte-compile and review: files in lower layers `require` nothing from
  higher ones.
- Core tests run without creating any buffer.
- No source file uses another file's `--` symbols (STD-004 lint).
