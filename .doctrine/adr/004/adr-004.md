# ADR-004: Sparse integer ranks with explicit redistribution

## Context

An entry's position in a queue is an `IW_<Q>` rank on the entry itself
(ADR-001), and every write goes through its buffer under the save policy
(ADR-002). SL-001 shipped append and tail rotation. SL-002 adds placement
between neighbours (REQ-009), so the rank scheme must answer what happens
when an entry goes *between* two others.

Forces:

- **Small diffs.** A move should change one line in one file (REQ-010).
  The user's notes are in Git, and every rewritten rank is noise in their
  history and a chance to collide with an unsaved buffer.
- **Exactness.** Ranks are compared and stored exactly. No rounding, and
  any tool reading the files (JSON, floats) sees the same value
  (REQ-023).
- **Gaps run out.** Any finite scheme that writes one entry per move
  eventually leaves two neighbours with no value between them.
- **Many files per queue.** Renumbering a queue touches every file that
  holds a member, often with unsaved buffers among them. That is a
  multi-file, non-atomic operation (REQ-019, REQ-020).

## Decision

We will rank queue members with sparse, exact integers, and renumber only
as explicit, user-approved maintenance.

1. **Domain.** A rank is an integer `r` with `|r| ≤ 2^53 − 1`. Negative
   ranks are valid and sort normally. Order is by rank, then by entry ID
   (`string<`). Anything else in an `IW_<Q>` value is an invalid rank,
   which excludes that membership.
2. **Spacing.** New ranks are laid out at a fixed power-of-two spacing,
   a core constant. Its value belongs to the design: SL-001 uses 1024.
3. **Allocation writes one entry.** Placement is computed over the order
   with the target removed (REQ-009). Then:
   - into an empty queue: the spacing;
   - after the last member: last + spacing;
   - before the first member: first − spacing;
   - between neighbours `L < R`: `floor((L + R) / 2)`, used only when it
     lies strictly between them.
   Only the target's rank is written. A placement that leaves the
   relative order unchanged writes nothing.
4. **No gap, no write.** If no allowed rank exists, either because the
   neighbours are adjacent or because the result would pass the limit,
   the operation stops before any change and says that redistribution is
   needed. It never renumbers silently or falls back to another scheme.
5. **Redistribution is maintenance.** Renumbering a queue, including the
   pending placement, re-lays every member at the spacing, in order. It
   runs only after the user approves a previewed plan, and it follows
   REQ-019 and REQ-020 (unsaved buffers, unwritable files, re-check before
   apply, failure report). It goes through the one write path (ADR-002,
   ADR-003).
6. **The core owns the arithmetic.** Rank domain, spacing, allocation and
   redistribution plans are pure core functions over plain data
   (ADR-003). No other layer computes a rank.

`IW_AFTER_<Q>` stays reserved and is never written. This ADR doesn't use
relative-position links.

## Consequences

### Positive

- An ordinary add, move or Continue changes one line in one file, so
  diffs and undo stay small.
- Exhaustion is loud and safe: the user sees a refusal and a plan, never
  a silent multi-file rewrite.
- Ranks are plain integers that any reader can sort correctly.

### Negative

- Repeated placement into the same gap halves it each time. With spacing
  `s`, about `log2 s` same-gap placements exhaust it (10 for 1024). Hot
  spots near the front, such as a default "after 2", will need occasional
  redistribution.
- Redistribution is a multi-file, non-atomic operation, recovered through
  Git (REQ-020), not a transaction.

### Neutral

- Ranks carry no meaning beyond order. Their values drift and are
  normalised only on request.
- Tail rotation (Continue to End) never exhausts internal gaps. It can only
  reach the upper limit, after about 2^43 rotations at spacing 1024.

### Rejected

- **Renumber on every move**, as in a dense 1..N scheme. Every move
  rewrites many entries across many files.
- **Floating-point ranks.** They are inexact, their precision runs out
  silently, and they read differently across tools.
- **Fractional indexing** (variable-length string keys, LexoRank). There
  is no exhaustion, but keys grow without bound, are opaque to read and
  edit by hand, and the extra machinery buys nothing at this scale.
- **Linked placement** (`IW_AFTER_<Q>` pointers). A move rewrites the
  neighbours' links across files, and broken chains need repair.

## Verification

- Core tests pin the domain bound and spacing as literals, and test each
  allocation case: empty, front, end, between, adjacent → nil, and limit
  → nil (STD-001 item 4).
- Command tests show that a move writes exactly one line, that a no-op
  placement leaves the file unmodified, and that exhaustion refuses with
  nothing changed (REQ-010 acceptance criteria).
- Review: no layer other than the core computes a rank (ADR-003,
  POL-002).
